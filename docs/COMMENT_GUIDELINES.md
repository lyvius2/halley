# 주석 작성 규칙

## 원칙

코드로 표현할 수 있는 내용은 이름, 작은 함수, 타입으로 드러낸다. 주석은 코드만으로 알기 어려운 의도와 제약을 보완할 때만 작성한다.

## 표준 형식

프로덕션 코드의 설명 주석은 선언 바로 앞에 쓰는 Javadoc 형식(`/** ... */`)을 표준으로 한다. 클래스·메서드·필드의 책임과 계약을 문서화할 때 사용한다.

테스트의 `// given`, `// when`, `// then`과 후속 작업을 표시하는 `// TODO`만 예외로 허용한다. 메서드 본문에 구현을 따라가는 설명 주석은 작성하지 않는다.

Swagger/OpenAPI 문서화가 적용된 Controller의 엔드포인트 설명은 Javadoc 대신 Swagger 애너테이션으로 작성한다. 요청·응답·오류 조건은 API 명세에 맞는 애너테이션 속성으로 문서화한다.

## 남기는 주석

- 외부 API·라이브러리·프로토콜의 비직관적인 제약
- 보안, 데이터 정합성, 성능, 장애 대응처럼 변경 시 문제가 될 수 있는 선택의 이유
- 코드만으로 즉시 알기 어려운 부작용이나 운영상 주의사항
- 공개 API의 사용 방법과 호출자가 알아야 할 계약
- 당장 처리할 수 없는 후속 작업. `TODO`에는 필요한 작업과 현재 미처리 사유를 함께 적는다.

## 작성하지 않는 주석

- 코드나 이름을 그대로 한국어로 반복하는 주석
- 설계 문서의 장·절·세션 번호나 구현 이력을 설명하는 주석
- `설계 문서 3장을 참고한다`처럼 문서의 특정 부분을 읽도록 지시하는 주석. 필요한 제약과 이유를 코드 가까이에 직접 적고, 상세 설계는 문서에서 관리한다.
- 모든 필드·메서드에 일괄적으로 붙이는 Javadoc
- 주석 처리한 코드, 작성자 표기, 변경 이력
- HTML·Markdown 태그로 꾸민 주석
- 다른 파일이나 모듈을 읽어야만 이해되는 모호한 설명

## Javadoc 작성 기준

- 클래스 Javadoc에는 클래스의 책임 또는 목적을 쓴다.
- 메서드 Javadoc에는 입력과 반환 결과를 쓴다. 반환값이 호출자에게 중요한 경우 `@return`으로 구체적으로 설명한다.
- `boolean` 반환값은 어떤 경우에 `true`이고 `false`인지 명확히 쓴다. `~인지 여부`처럼 모호하게 표현하지 않는다.
- 예외를 호출자에게 전달하는 경우 `@throws`에 예외 타입과 발생 조건을 쓴다. 예외 클래스는 어떤 상황에서 던지는지 설명한다.
- 구현 순서, 반복문, 현재 사용하는 자료구조처럼 구현 변경에 따라 거짓이 되는 설명은 적지 않는다.
- `@deprecated`에는 대체 API와 사용 중단 사유를 쓴다. `@author`와 변경 이력은 Git으로 관리하므로 쓰지 않는다.
- 관련 API를 가리킬 때만 `{@link}`를, 코드 조각을 표시할 때만 `{@code}`를 사용한다. HTML 태그는 사용하지 않는다.

## 문체

- 한 문장으로 역할 또는 선택 이유를 명확히 쓴다. 장황한 배경 설명은 문서나 이슈로 옮긴다.
- 자연스러운 한국어를 사용한다. `여기서`, `이것`, `그때` 같은 지시어와 구어체는 피한다.
- 사실과 제약을 직접 쓴다. 예: `캐시 조회 실패 시 외부 API를 다시 호출한다.`
- HTML 태그를 사용하지 않는다. Javadoc 태그는 호출자에게 필요한 정보를 전달할 때만 사용한다.
- 모든 선언에 Javadoc을 의무적으로 작성하지 않는다. 공개 API와 코드만으로 계약을 파악하기 어려운 선언에만 작성한다.

## 점검 기준

주석을 작성하거나 수정할 때 다음 질문에 모두 답할 수 있어야 한다.

1. 이 내용을 코드의 이름이나 구조로 표현할 수 없는가?
2. 이 주석이 없으면 변경 시 잘못 이해할 가능성이 있는가?
3. 코드가 바뀌어도 주석이 사실로 유지되는가?
4. 한 번 읽고 바로 이해되는가?
