# 단지명 매칭 — LLM을 쓸 것인가

> **검토 문서입니다. 아직 구현하지 않았습니다.**
> 결론부터: **LLM은 마지막 수단이고, 그 앞에 더 싸고 확실한 수단이 둘 있습니다.**

---

## 무슨 문제인가

```
501건을 받았지만 '한화포레나정릉'과 이름이 맞는 거래가 없습니다.
```

국토부 실거래를 찾을 때 **단지명이 열쇠**입니다. 그런데 두 이름이 서로 다릅니다.

| 우리 매물명 | 국토부 표기 | 지금 |
|---|---|---|
| `상계주공7단지` | `상계주공7(고층)` | ✅ 괄호를 버려 맞춥니다 (I230) |
| `한화포레나정릉` | `정릉꿈에그린`(추정) | ❌ **글자가 하나도 안 겹칩니다** |

**한화포레나정릉은 브랜드가 바뀐 단지입니다.** 대우 `푸르지오` → 한화 `꿈에그린` →
`포레나` 로 이어진 계열이라, 국토부에 옛 이름으로 남아 있으면
<b>부분 문자열 비교로는 영원히 안 맞습니다.</b>

지금 규칙(`ComplexName.same`)은 이렇습니다.

```java
normalize → 괄호와 내용 제거 · "아파트" 제거 · 공백/·/- 제거 · 소문자
same     → 서로 포함이면 같다
```

**표기 흔들림**은 잡지만 **이름이 통째로 바뀐 것**은 못 잡습니다. 다른 종류의 문제입니다.

---

## 후보 넷

### ① 주소로 좁힌다 — **가장 싸고 확실합니다**

국토부 응답에 이미 옵니다. **지금은 파싱조차 안 합니다.**

```xml
<umdNm>상계동</umdNm>     ← 법정동
<jibun>691</jibun>        ← 번지
<bonbun>0691</bonbun> <bubun>0000</bubun>
```

우리 매물에도 지번주소가 있습니다 — `서울시 노원구 상계동 692`.

```
동이 다르면      → 다른 단지다 (이름을 볼 것도 없다)
동+번지가 같으면 → 이름이 달라도 같은 단지다   ← 브랜드 변경을 잡는다
```

**이것 하나로 한화포레나정릉이 풀립니다.** LLM도, 사전도 필요 없습니다.

> 다만 **번지가 여러 개인 대단지**가 있습니다. 그때는 동까지만 맞추고
> 면적으로 갈라야 합니다. 번지가 다르다고 곧바로 배제하면 안 됩니다.

### ② 단지 사전을 만든다 — 확실하지만 손이 갑니다

국토부 응답의 `aptSeq`(예: `11350-41`)는 **단지 식별자**로 보입니다.
매물을 한 번 맞춘 뒤 `(우리 매물 id → aptSeq)` 를 저장해 두면 다음부터는
이름을 안 봐도 됩니다.

- **장점**: 한 번 맞추면 영구적이고 공짜입니다
- **단점**: **처음 한 번을 맞춰야** 합니다 — 그게 지금 문제입니다.
  ①이나 ③으로 처음을 넘긴 뒤 사전에 넣는 조합이 맞습니다

### ③ 사람이 고른다 — 가장 정직합니다

이름이 안 맞을 때 **같은 동의 단지 목록**을 보여 주고 고르게 합니다.
지금도 이미 "이름이 맞는 거래가 없습니다"를 띄우고 있으니, 그 자리에
후보를 늘어놓으면 됩니다.

```
'한화포레나정릉' 과 맞는 거래가 없습니다.
정릉동에서 거래된 단지 — 어느 것입니까?
  ○ 정릉꿈에그린    (84.9㎡ 외 3개 평형 · 12건)
  ○ 정릉힐스테이트  (59.9㎡ 외 2개 평형 · 7건)
  ○ 아니오, 없습니다
```

고른 결과는 ②의 사전에 넣습니다. **한 번만 고르면 됩니다.**

### ④ LLM에게 묻는다 — 가능하지만 마지막입니다

같은 동의 단지명 목록과 우리 매물명을 주고 "같은 단지가 있나" 묻습니다.
브랜드 변경 이력은 **LLM이 아는 종류의 지식**이라 실제로 맞힐 가능성이 높습니다.

```
매물: 한화포레나정릉 (서울 성북구 정릉동, 전용 84.9㎡, 2021년 준공)
정릉동에서 거래된 단지: 정릉꿈에그린 · 정릉힐스테이트 · 정릉e편한세상 · …
같은 단지가 있습니까? 없으면 없다고 하십시오.
```

**하지만 위험이 큽니다.**

- **틀려도 티가 안 납니다.** "정릉꿈에그린이 맞습니다"라고 하면 그럴듯해서
  아무도 의심하지 않습니다. 그리고 그 시세가 <b>이 매물의 참고값</b>이 됩니다
- 이 프로젝트는 이미 [I210]에서 **LLM 추정을 표시하고 다시 물어보게** 만들었습니다.
  같은 장치가 여기도 필요합니다
- 매물마다 한 번씩 부르면 [I217]에서 겪은 **비용·지연** 문제가 반복됩니다

## 제안하는 순서

```
① 동·번지로 좁힌다          ← 먼저. 공짜고 확실하다
      ↓ 그래도 못 찾으면
③ 후보를 보여 주고 고르게    ← 사람이 아는 것을 묻는다
      ↓ 고른 결과를
② 사전에 저장               ← 다음부터는 안 묻는다
      ↓ 그래도 남는 것에만
④ LLM 에게 제안만 시킨다     ← 확정이 아니라 <b>추천</b>으로
```

④를 쓴다면 **반드시 이렇게** 해야 합니다.

- **자동으로 확정하지 않습니다.** "이 단지 아닐까요?"로 띄우고 사람이 승인합니다
- 승인한 것만 사전(②)에 들어갑니다
- 같은 동 안에서만 묻습니다 — 후보를 좁혀야 헛소리가 줄어듭니다
- 매물당 한 번만 묻고 결과를 남깁니다 (성공이든 실패든)

---

## 왜 지금 안 하는가

**①을 아직 안 했습니다.** 국토부가 이미 주고 있는 `umdNm`·`jibun` 을
<b>파싱조차 안 하는 상태</b>에서 LLM을 붙이는 것은 순서가 틀렸습니다.

①만 해도 한화포레나정릉은 풀릴 가능성이 큽니다. 그러고도 남는 것이 있으면
그때 ③, 그다음에 ④입니다.

> 이 프로젝트에서 반복된 교훈입니다 — [I219](10건만 받고 있었다),
> [I230](규칙이 두 벌이었다), [I233](파서는 멀쩡했다). **이미 있는 데이터를
> 안 쓰고 있는지부터** 봐야 합니다.
